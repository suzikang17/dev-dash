Beyond Git: jj, Fossil & the Queryable Project Store

What "replacing git" really means — and how lore + dev-dash already implement most of the synthesis jj and Fossil are circling.

2026-06-30Scope: landscape → concept → codebase findings~/dev/lore · ~/dev-dash

01 · Landscape

"Replacing git" means replacing the interface, not the model

Git's content-addressed commit DAG is the part everyone agrees is correct. The future isn't "git is gone" — it's "you stop typing git and the porcelain changes." The complaints: bad CLI, heavyweight branching/merging, poor monorepo scale, binary bloat.

  • jj — git-compatible frontend; the credible "what replaces the command" answer.
  • Sapling — cleaner UX + stacked diffs over git; strong at scale.
  • Pijul/Darcs — true theoretical replacement (patch theory); niche, breaks git compat.
  • Fossil — all-in-one VCS + issues + wiki + forum; deliberate niche.

Only interoperability has ever driven adoption — speak git's format, migrate one dev at a time. Git the storage format is permanent infrastructure; what gets replaced is the command you type.

02 · The two bets

jj vs Fossil

Jujutsu — UX is wrong, model is right

  • New frontend, backend is git's object store — a jj repo is a git repo
  • No staging — working copy is a commit, auto-snapshotted
  • Total undo — op log + jj op restore rewinds the whole repo
  • Conflicts are data — rebase through them, never blocked
  • Adoption risk ≈ 0; reversible. Bites: pre-1.0, no-staging flip

Fossil — VCS shouldn't be standalone

  • By SQLite's author; one SQLite file = whole project
  • Issues + wiki versioned with code, not in a silo
  • Remembers everything — anti-history-rewrite by design
  • Native web timeline + UI, zero setup
  • Bites: not git-compatible → leaves the ecosystem

Workspaces (jj's worktrees): jj workspace add ../dir — independent dirs, shared repo + op log, no branch required, each with its own working-copy commit. Docs cite the use case explicitly: give AI agents their own sandbox.

03 · Fossil's breadth

Where the all-in-one scope falls short

Fossil bundles a lot, but the scope is wide, fixed, and pre-AI:

  • No code review / PR workflow — timeline + tickets, but no first-class pull requests.
  • No CI/CD — no pipeline integration; bolt-on, against the grain.
  • One-way git interop only — isolates you from GitHub and every AI coding tool that assumes git.
  • Fixed artifact types — check-ins / tickets / wiki / forum; no extensible typed-doc schema.
  • Not agent-native — queryable SQLite, but no schema-as-prompt, no owner: ai, no machine-owned sections.
  • No operation log / undo — faithful history ≠ rewindable state.
  • No real-time event/hook stream — pull-based; nothing like a live agent event bus.

Punchline

These gaps are almost exactly what lore + dev-dash add on top of git. Building on git instead of inside Fossil gets you Fossil's "one queryable place" benefit and the things its fixed, pre-AI breadth misses.

04 · Concept

The bridge between jj and Fossil

jj's op log is an event database that doesn't know it's one. Fossil's repo is a database that won't branch like git. Same target, opposite sides:

A project as an event-sourced, queryable, branchable store — code, operation history, issues, and decisions all first-class records you can SELECT, fork, time-travel, and safely undo.

Convergence is already happening: git-bug / Radicle pull Fossil's bundling into git; Dolt / Datomic pull git's branchable DAG into a database. Nobody's shipped the full thing.

Key insight

"A VCS" and "a queryable project database" are the same data structure from two angles — an append-only log of facts with a branchable index. jj is the strongest engine; Fossil the strongest vision of scope.

05 · Finding

lore — a queryable knowledge store on git, not in a DB

Node CLI at ~/dev/lore. A git-native knowledge base over plain markdown: markdown is source of truth, index.md is a regenerable view. Deliberately not a database (deps: gray-matter, yaml, zod).

  • Typed docs as data — task / ticket / decision / devlog / idea / artifact / policy, defined by YAML schemas (eject to override). The schema is the type system and an AI prompt.
  • Graph layer — type: reference fields + [[wikilinks]] → on-demand backlinks (never persisted).
  • History — mostly flat current-state; two append-only seams (## Status history, dated devlogs). Git is the real event log & time machine.
  • Agent-native by design (ADR 0012) — a policy type whose frontmatter is routing metadata (applies_to, trigger, status, priority); the app injects active, scope-matched policy bodies deterministically into agent prompts. Edit a doc → change agent behavior, no code change. This is exactly what Fossil's fixed scope can't do.

The match

lore is a Fossil-style knowledge store that made the opposite storage bet from Fossil — the same as jj: don't use a database, treat git as the time machine. You built the queryable knowledge layer on top of git.

Event-log vs current-state, made explicit (ADR 0012)

"An ADR is decision history (immutable: why we chose this). A policy doc is a living operating instruction the agent follows now (editable; deprecated when superseded). Don't conflate them." That's the append-only-record vs mutable-current-state split — the two halves of the whole synthesis — already separated as first-class doc types.

Drift flagged: README claims a claude -p fallback for AI commands; the code only uses the Anthropic SDK and hard-errors without ANTHROPIC_API_KEY.

06 · Finding

dev-dash — unifying code-history with project-knowledge

macOS SwiftUI dashboard treating knowledge (devlogs/decisions/tasks) and code history (git/Claude sessions) as one file-backed graph, with agents as first-class participants.

  • Scanners — git readers (GitScanner, RecentCommitsScanner, GitStatusScanner incl. git worktree list) + knowledge graph (LoreLinkIndex builds two-way links in Swift).
  • WorktreeManager — N tasks → N worktrees (task/<id>-<slug>) → N Claude sessions; the task lore doc is the join between agent, branch, worktree. Hand-rolled safety (collision-retry, branch -D HEAD guard).
  • Hook event bus (ADR 0004) — makes any Claude session an event source; recentEvents is a live op-log of agent activity, but in-memory, 300-capped, never persisted.
  • Session JSONL transcripts — append-only log of every tool call; the closest thing to true event sourcing, already on disk.
  • PolicyStore (ADR 0012) — reads policy docs; DashboardStore.policies(for:appliesTo:trigger:) returns active, scope+trigger-matched policies ordered by (priority, id), injected into ticket-breakdown and the agent seed prompt. Behavior-as-data the agent reads at launch.

The loop

Launch agent into isolated worktree → agent acts (hook events) + writes lore docs → dev-dash reduces events into live state + re-renders the graph. cwd is the join key. = a queryable, agent-aware event/knowledge graph layered on git.

08 · The gap & the fix

The missing 20% is jj's deepest idea

Four append-only streams exist (status history, hook bus, JSONL, devlogs) — but the richest (hook bus) is ephemeral, and there's no general undo / time-travel. Agent off the rails = manual git, not "rewind to operation 12."

What jj gives you — and doesn't

  • Gives: repo-level op restore across all workspaces; retires WorktreeManager's safety code; first-class conflicts for N agents; durable op-log for free; stays git so lore/CI/PRs unchanged.
  • Doesn't: reverse external side effects (PR opened, Linear moved), app/in-memory state, or anything outside the repo. Necessary but not sufficient.

Why op-log ranks first, jj second

jj's op-log and your hook bus are the same structure from two sides. jj covers the code half of undo cheaply; your own event log covers the knowledge/external half jj can't touch. Build the log first; treat jj as a measured spike.

09 · Action

Next moves (value-per-effort order)

  1. Persist the hook event bus → append-only per-project NDJSON. You already produce the stream; instant durable op-log. Commit to this.
  2. Unify the durable seams (status history + hook events + JSONL) into one timeline keyed by task/cwd — the "SELECT across code + knowledge + activity, as-of any point" surface.
  3. Spike jj behind launchInWorktree — swap WorktreeManager.create for jj workspace add on one project. Evaluate, don't migrate. Note: GitStatusScanner.parseWorktrees needs a jj workspace list variant (jj workspaces aren't git worktrees).
