# Impeccable — Project Design Context

## Design Context

### Users
**One user: the developer who builds it (suki).** dev-dash is an explicit *personal tool* — the in-app roadmap literally states "You are the user. Build for yourself, use it daily, fix what actually annoys you." There is no external audience to design for and no marketing surface.

- **Context of use:** Opened many times a day while context-switching between local dev projects. Lives inside a native macOS SwiftUI app; the design surface in question is the per-project **Product tab** — a self-contained tabbed living-doc (`docs/devdash/index.html`) rendered in a WKWebView.
- **Job to be done:** A single living context that is *both* human-readable *and* AI-parsable. Plan features, write PRDs/plans, track goals & KPIs, log decisions, sketch notes in an outliner, triage ideas. Files on disk are the source of truth so AI tools (Claude Code, scripts, grep) read/write them directly — no database, no server.
- **Emotional goal:** Reduce context-loss friction. Opening it should feel like sitting back down at a familiar, well-organized workbench — instantly oriented, not greeted by a generic admin panel.

### Brand Personality
Three words: **precise · warm · a-little-weird.**

A workshop instrument with personality. It should read as *honestly a developer's tool* — dense, data-forward, unafraid of monospace and tabular numbers where they earn their place — while carrying the warmth and small idiosyncrasies of something handmade for an audience of one. Opinionated, not corporate. Lived-in, not sterile. It can make choices a shipped product never could because nobody has to be onboarded to it but the maker.

Voice in UI copy: terse, knowing, occasionally dry. Labels over sentences. No marketing tone, no exclamation points, no "Welcome!" — but empty states can have a wink.

### Aesthetic Direction
A blend of **engineering-terminal / utilitarian** and **warm / tactile / slightly weird**:

- **Utilitarian backbone:** information density is a feature, not a flaw. Tabular numerics, real tables, tight vertical rhythm, monospace for data/metadata/IDs/timestamps where it conveys meaning (NOT as blanket "techie" decoration). Reads like a precision instrument's panel.
- **Warm/tactile overlay:** the *material* should feel deliberately chosen and a touch handmade — a warm-tinted neutral ground rather than cold slate-blue, one confident accent hue that is emphatically **not** the cyan-glow AI default, small idiosyncratic detailing (considered dividers, intentional empty states, a distinctive display face for headings). Memorable enough that the maker recognizes it as *theirs*.
- **Both themes, both designed.** Keep the `prefers-color-scheme` branch, but each variant must be genuinely composed — not a mechanical invert. Dark = a warm-charcoal workshop at night. Light = a calm paper/drafting-table surface by day.

**Anti-references (do NOT look like this):**
- The current default-ish styling this redesign replaces: `border-left` accent stripes on callouts/blockquotes, cyan-on-dark (`#5ac8fa`), system-font-only stack, uniform bordered rounded cards repeated everywhere.
- Generic SaaS admin dashboard / Linear-clone / shadcn-default look.
- The AI-slop palette: cyan-on-dark, purple→blue gradients, neon accents, glowing dark mode.
- Glassmorphism, gradient text, hero-metric template, sparkline-as-decoration.

### Design Principles
1. **Honest density.** This is a power tool for its only user. Pack information tightly and trust the reader; don't pad with whitespace meant to reassure strangers. But density ≠ noise — use rhythm and typographic hierarchy, not boxes, to separate things.
2. **Warm, committed color.** One brand hue, chosen on purpose (not cyan, not the default blue). Tint every neutral subtly toward it via OKLCH so dark and light both feel like one material. Accent is rare (≈10% weight) so it still means something.
3. **Monospace with intent, not as costume.** Mono earns its place on data, metadata, timestamps, code, IDs, keyboard hints — never on prose or as a blanket "developer vibe." Pair a distinctive display/text face (avoid the reflex fonts — no Inter, IBM Plex, Space Mono/Grotesk, Fraunces, etc.) with a refined mono.
4. **No accent stripes, no card-soup.** Replace the `border-left` callout pattern entirely. Differentiate regions with full borders, background tints, leading glyphs, or nothing — never a colored side-stripe. Don't wrap everything in a bordered rounded card; flatten where possible.
5. **Two real themes.** Light and dark are each composed deliberately and must both pass contrast; light is not an afterthought invert.
6. **Personality lives in the details.** Empty states that teach (with a dry wink), considered dividers, a distinctive heading face, intentional motion on the one page-load moment — the touches that make the maker say "that's mine," not "which AI made this?"

### Technical Constraints (carry into any implementation)
- Output is a **single self-contained HTML file** generated by `Sources/DevDash/Scanners/ProductDocGenerator.swift` — one embedded `<style>` block, **no build step**, no CSS framework.
- Rendered via WKWebView `loadFileURL` (a `file://` origin). Implications: **no network requests** — any web font or library must be bundled locally under `docs/devdash/.assets/`; **never** use `file://…#fragment` navigation or `history.replaceState` (WKWebView blocks it as cross-origin). Tab switching is pure DOM class-toggling.
- Interactivity uses **Alpine.js** (bundled locally at `.assets/alpine.min.js`). Prefer declarative `x-data`/`x-for`/`@click`/`x-show` over imperative DOM injection.
- Files on disk remain the source of truth and must stay **AI-editable** — keep markup semantic and legible; no opaque generated soup.
- Respect `prefers-reduced-motion`. Animate transform/opacity only.

### Status
Context-setup only (teach). No design changes have been made yet. When ready, the likely first target is the visual system (typography + color + the callout/card/blockquote patterns) baked into `ProductDocGenerator.swift`'s stylesheet.
